## 0. 文档用途

本 Art Bible 是 ZCamp 所有玩家可见表现的共同依据，用于统一：

- 场景、建筑、塔、敌人、Boss、UI、图标、动画和 VFX 的视觉语言；
- 内部制作、外包需求、AI 辅助出图和最终验收的标准；
- “什么应该做”和“什么不应该做”的边界；
- MVP 阶段的资产优先级与性能预算。

标记约定：

- **已定**：除非产品方向变化，否则按此执行；
- **工作标准**：首轮制作采用，实机验证后允许调整；
- **待定**：需要概念稿或实际运行画面支持后再锁定。

当本文与玩法文档冲突时，玩法规则以产品与核心模拟为准；玩家可见的视觉表达以本文为准。

## 1. 视觉北极星

### 1.1 一句话方向【已定】

> **块面卡通尸潮防线：绝大部分画面属于不断逼近的尸潮，玩家只守着城墙后方一小块清晰、温暖、可经营的阵地。**

### 1.2 核心关键词【已定】

**块面卡通、粗外轮廓、两档明暗、大头短肢、强功能色、轻黑色幽默、清晰、温暖、压迫。**

### 1.3 玩家应感受到的情绪

1. 修整时：这是“我的营地”，小而温暖，值得经营；
2. 开波时：危险正在从黑暗中涌来；
3. 战斗时：防线像一台机器一样清晰、高效、令人满足；
4. 强化时：我正在塑造一种越来越鲜明的战斗流派；
5. 失败时：营地真的被攻破，而不是一个数值简单归零；
6. 胜利时：黎明、灯光或营火让玩家感到“守住了”。

### 1.4 视觉设计支柱【已定】

#### 支柱 A：一眼读懂

玩家在手机屏幕上应能迅速识别进攻方向、城墙状态、塔种、危险敌人和下一步主操作。轮廓、动势和位置优先于纹理细节。

#### 支柱 B：温暖对抗威胁

营地用暖光与稳定几何表达安全；尸潮用冷暗环境、不对称轮廓和群体运动表达威胁。

#### 支柱 C：小模型也要像完整世界

画面可以低细节，但不能像开发面板。道路、边界、墙体、灯光、塔位和营地核心必须共同组成一个完整物件。

#### 支柱 D：模块化获得完成度

用共用底座、基础身体、覆盖件、功能色和程序动画派生内容，不为每个单位制作完全独立的高成本资产。

#### 支柱 E：反馈有节奏，不靠噪声

每种塔、每类关键敌人和每个重要事件只保留一个招牌反馈。反馈必须帮助读局，不能淹没战场。

### 1.5 明确不做【已定】

- 不做写实血腥、写实材质或沉重恐怖；
- 不做依赖大量骨骼或逐帧动画的高规格角色演出；
- 不做所有元素都高饱和、全屏同时闪烁的“彩虹战场”；
- 不以换色作为区分所有敌人和塔的唯一手段；
- 不做与玩法无关的复杂末日军事 HUD；
- 不让长段说明文字长期占据主战场；
- 不为了“丰富”堆放遮挡路线与单位的环境装饰。

## 2. 参考体系与借鉴边界

| 参考对象 | 在 ZCamp 中负责什么 | 借鉴 | 不借鉴 |
|---|---|---|---|
| **Isle of Arrows** | 主美术参考 | 微缩棋盘、统一视角、模块化建筑、克制 UI、整体完成度 | 明亮中世纪主题、自由拼路玩法 |
| **Lucky Defense** | 竖屏构图参考 | 顶部状态、中部战场、底部操作；有限格位；关键时刻的包装 | 角色收集与商业化信息密度 |
| **Thronefall** | 光照和群潮参考 | 暖色安全区、夜战压暗、低细节敌群、阶段光照差 | 英雄直控、横向大地图 |
| **Kingdom Rush** | 战斗语法参考 | 塔种剪影、炮/冰/电反馈差异、敌人威胁辨识 | 大量手绘逐帧动画与内容规模 |
| **Dead Ahead** | 僵尸题材参考 | 轻黑色幽默、残破服饰、模块化角色、暖色枪火 | 横版出兵与高频断肢血腥 |

参考对象用于回答不同问题，不要求最终画面像任何一款现有产品。ZCamp 的独特组合是：**竖屏固定营地 + 夜战暖光 + 微缩模型 + 玩具感尸潮。**

### 2.1 休闲轻度护栏【已定】

- 《Isle of Arrows》是造型复杂度、表面洁净度和微缩棋盘完成度的主参考；不能只取“微缩”而丢掉它的轻盈与概括；
- 《Lucky Defense》用于校准移动端的高明度、圆润角色、清楚轮廓和低材质噪声；
- 战斗地面保持中等明度，屏幕中央不得大面积压黑；暗部主要用于外围框景、UI 阴影和纵深，而不是覆盖可玩区；
- 环境和建筑以大色块、柔和渐变、少量磨损表达，不使用写实湿地、颗粒噪声、复杂金属反射和密集碎石堆砌完成度；
- “低材质噪声”只限制随机颗粒和无意义细节，不允许退化成廉价低模或扁平塑料：建筑、单位和 UI 必须有厚实主形、清楚倒角、材质分层、受控高光、环境遮蔽与稳定接触阴影；
- 商品感来自精确比例、干净轮廓、统一受光和局部精细度，不来自写实纹理、满屏反射或压暗曝光；
- 普通僵尸采用大头、短肢、夸张表情和玩具比例；压迫感来自数量、纵深和体型差，不来自写实恐怖；
- 缩小到 20% 查看时，首先读到尸潮、城墙、15 格和四卡，而不是材质细节。

## 3. 画面构图与镜头

### 3.1 逻辑画布【已定】

- 基准分辨率：720×1280；
- 画面方向：竖屏；
- 基准安全边距：左右 24、顶部 24、底部 24 个逻辑像素；
- 所有关键文本和交互不得压在设备刘海、圆角或系统手势区附近；
- 首轮以 9:16 为主，同时验证较矮与较长的移动端比例。

### 3.2 竖屏分区【工作标准】

| 区域 | 建议高度 | 职责 |
|---|---:|---|
| 顶部 HUD | 约 6%～8% | 波次、剩余敌人、暂停；资源可下沉到底栏 |
| 尸潮战区 | 约 56% | 敌人入口、单一纵向推进区、Boss 与群潮；全屏绝对主体 |
| 城墙分界 | 约 4% | 城墙本体、耐久、攻墙反馈与最后防线 |
| 5×3 建造区 | 约 25% | 15 个固定横向格、营地建筑、建造/升级操作 |
| 木材轨道 + 底部手牌 | 约 15% | 四卡横排、建造资源与选择状态 |

HUD 直接叠加在尸潮战区顶部，不为它切出独立横条。5×3 格区宁可使用横向较宽、纵向较浅的地基，也不能向上侵占敌军空间。底部四卡手牌在战斗中保持固定位置，不设置开波按钮。

### 3.3 战场叙事方向【已定】

- 敌人从画面上方的黑暗/雾区进入；
- 敌人在城墙上方的单一纵向战区中由上向下推进；
- 城墙横跨画面，是危险区与营地区的明确分界；
- 城墙后方完整呈现 5 列×3 行固定建造格；
- 防御建筑从格区越过城墙向上攻击，经济与营地建筑留在格区内形成经营感；
- 营地核心与暖光融入 5×3 格区及其边界，不另占一块会破坏棋盘识别的区域。

从上到下的视觉叙事应是：**未知黑暗 → 尸潮通道 → 火力杀伤区 → 城墙 → 温暖营地。**

### 3.4 视角【工作标准】

- 使用固定的 3/4 俯视或伪等距视角；
- 资产可由 2D 矢量、分层位图或预渲染模型制成，不要求实时 3D；
- 所有建筑与单位必须共享相同俯视角和受光方向；
- 镜头不旋转，常态不平移；
- 只在 Boss 入场、城墙重击和胜负时使用轻微缩放或震动。

### 3.5 视觉尺度【工作标准】

- 普通僵尸是全局尺度基准 1.0；
- 快速敌人约 0.80～0.90；
- 重装敌人约 1.20～1.35；
- 精英在基础身体上增加 10%～20% 体量或专属覆盖件；
- Boss 至少是普通敌人的 1.8 倍，并具有不同于普通敌人的顶部轮廓；
- 城墙必须在不看血条时也像“最后防线”。

### 3.6 5×3 建造格【已定】

产品定义中的 5 列×3 行、共 15 个建筑格是主战场不可变的空间骨架，不再把建筑映射到道路两侧。当前原型若仍只有 10 个槽位，应视为实现待对齐项，不能反向改变美术与交互规范。

- 前排贴近城墙，优先表达防御、维修和承伤；
- 中排承担防御与支援混合功能；
- 后排靠近营地内部，优先表达经济和主基地；
- 常态用地砖、铆钉、木框或地基把格子融入场景，不画成开发网格；
- 进入建造态后，15 个合法格必须同时清楚可见；已占用、可建造、不可建造和选中状态使用形状与亮度双重区分；
- 战斗与修整阶段不移动棋盘、不改变格子编号，保持空间记忆；
- 720×1280 下从完整格区起稿，再验证单格视觉尺寸与至少 56×56 的触控热区。

### 4.1 基础调色板【工作标准】

| 语义 | 色值 | 用法 |
|---|---|---|
| 画布边缘植被 | `#317A24` | 战场左右框景与纵深边界 |
| 植被高光 | `#4B9A29` | 树冠和灌木的一档受光面 |
| 战场赭黄 | `#E0A51E` | 尸潮战区大面积底色 |
| 道路高光 | `#EFBD37` | 中央推进通道和受光面 |

| 次文字 / 卡边 | `#D8C59B` | 标签、说明和卡片描边 |
| 建筑区橄榄绿 | `#7D9B2B` | 5×3 棋盘底面 |

| 中性装甲 | `#788087` | 城墙金属、塔底座和中性 UI |
| 僵尸灰绿 | `#69B64A` | 普通尸群主体 |

| 火炮橙红 | `#F07B28` | 炮弹、爆炸、灼烧 |

以上色值是起始令牌，不是要求所有资产使用纯平色。材质可以围绕令牌做明暗与灰度变化。

### 4.2 色彩使用规则【已定】

1. 赭黄战场与橄榄绿边缘合计占画面约 55%～65%，保持明亮但不盖过单位；
2. 防守格、木色 UI 与城墙合计约 25%～30%，形成小而稳定的玩家阵地；
3. 塔种、爆炸、冰、电和危险色等高饱和功能色合计不超过约 15%；
4. 危险红不用于普通按钮和无风险装饰；
5. 四种塔的功能色在塔体、卡片、弹道、升级图标中保持一致；
6. 精英和 Boss 不能只靠颜色区分，必须同时改变轮廓、体型或入场方式；
7. 画面转为灰度后，营地、道路、敌人和主要按钮仍应分层清晰。

### 4.3 阶段光照【工作标准】

#### 波间商店阶段

- 环境较明亮、雾较薄；
- 营地灯光稳定；
- 塔位与可操作对象边缘更清晰；
- 商店关闭操作属于商店层，不在主战场常驻；
- 商店关闭后，战场中央显示清楚但不可点击的 `3—2—1` 倒计时；
- 倒计时结束，尸潮入口脉冲并自动开波。

#### 战斗阶段

- 环境整体压暗约 8%～12%；
- 营地暖光、枪火和弹道相对更亮；
- 尸潮入口出现低频红色警示或雾中脉冲；
- 底部托盘降低存在感。

#### 强化阶段

- 战场仍可见，但降亮度、降对比；
- 强化卡片是唯一高对比焦点；
- 选择后用一道短促能量流回到对应塔/城墙/HUD。

#### 胜利与失败

- 胜利：黑暗退去或营地暖光增强；
- 失败：暖光熄灭、墙体破口成为构图中心；
- 不使用与战场完全割裂的纯色全屏结果页。

## 5. 形状与材质语言

### 5.1 人类营地

- 形状：稳定、方正、有支撑结构，局部圆角；每个建筑控制在 4～6 个主要形块；
- 轮廓：只保留能识别功能的木桩、钢板、支架或旗帜，不堆叠小零件；
- 材质：用平涂色块与一档阴影暗示木材、金属和帆布，不绘制写实纹理；
- 状态：虽破旧但维护有序，体现“活人正在经营”。

### 5.2 僵尸与感染物

- 形状：大头、短粗四肢、前倾与不对称；普通敌人只保留少量大形；
- 轮廓：弯背、伸臂、拖步、破布、感染块；
- 材质：灰绿皮肤、低饱和服饰、两档明暗与一个小高光，不使用皮肤或布料微纹理；
- 气质：怪异但不过度恶心，允许轻微荒诞和黑色幽默。

### 5.3 防御塔

- 形状：底座稳定，顶部模块决定功能；每塔控制在 4～6 个主要组件；
- 轮廓优先：缩小到 48px 左右仍可凭外形辨认；
- 材质与营地一致，避免每座塔像来自不同游戏；
- 功能色是局部灯光、弹药或能量，不覆盖整个塔体。

### 5.4 UI

- 形状：厚实、简洁、轻度圆角；粗外轮廓与单一内高光建立层级；
- 材质：深色木质 / 石质大色块，不增加铆钉、划痕和细碎装饰；
- 不做过度科幻的全息玻璃；
- 面板可以有世界观味道，但文字区必须干净。

## 6. 场景与营地

### 6.1 场景层级【已定】

从后到前：

1. 夜空/远雾；
2. 荒地底面；
3. 道路与边缘；
4. 不可交互环境装饰；
5. 建造台与建筑；
6. 敌人、弹道和掉落物；
7. 前景雾、火星、局部遮罩；
8. HUD 和情境提示。

### 6.2 战场必备元素

- 尸潮入口：雾、破路牌、暗红警示或远处眼光；
- 主道路：清晰连续，不被装饰切断；
- 建造台：空、可建造、选中、不可建造、可升级五种状态；
- 城墙：主体、门/缺口暗示、耐久阶段覆盖层；
- 营地核心：暖光、帐篷/指挥车/篝火等生活痕迹；
- 边界：通过地形落差、围栏、废车或黑暗自然收边。

### 6.3 环境装饰规则

- 装饰聚集在道路之外和画面边缘；
- 每屏最多设置 2～3 个显眼叙事道具；
- 不使用与可交互建筑相似的轮廓或功能色；
- 废车、木箱、路障、探照灯、地面裂纹和旗帜应模块化复用；
- 雾与烟不遮挡敌人头部、血条和城墙状态。

城墙本体只负责阻挡、破损和承载耐久信息，不放置固定炮塔。四类防御塔必须位于 5×3 格内；前排格紧贴墙后，塔可以越墙射击，但塔的底座和血量语义始终属于格位。

### 6.4 城墙耐久视觉

| 耐久 | 视觉状态 |
|---:|---|
| 76%～100% | 完整墙体、稳定灯光 |
| 51%～75% | 小裂纹、少量碎屑 |
| 26%～50% | 明显裂口、灯光闪烁、局部烟尘 |
| 1%～25% | 大裂口、红色警示、持续火花/尘屑 |
| 0% | 破口、灯光熄灭、敌人突破构图 |

耐久变化应由覆盖层实现，避免为每一级城墙制作完全独立的整套资产。

## 7. 四类防御塔

### 7.1 共用结构【已定】

四类塔共用：基础建造台、底座材质、阵营灯、升级连接件和阴影。顶部功能模块决定塔种。

| 塔种 | 主轮廓 | 功能色 | 攻击节奏 | 招牌反馈 |
|---|---|---|---|---|
| 机枪塔 | 细长双枪管、弹链/弹箱 | 机枪黄 | 高频、短促 | 枪口跳动、黄白曳光、轻后坐 |
| 炮塔 | 短粗炮管、宽大炮座 | 火炮橙红 | 慢、重 | 大后坐、抛射、圆形爆炸、短停顿 |
| 冰冻塔 | 冷凝罐、晶体或环形喷口 | 冰冻青蓝 | 稳定脉冲 | 冰片/冷雾、敌人降饱和、脚下霜层 |
| 电磁塔 | 叉状天线、线圈、绝缘环 | 电磁紫白 | 瞬时、跳跃 | 折线电弧、白芯紫边、短暂残影 |

### 7.2 等级成长语言【工作标准】

- Lv.1：功能完整、结构简洁、单一灯源；
- Lv.2：增加支架、装甲、供能部件或第二灯源；
- Lv.3：增加能改变顶部轮廓的标志性模块；
- 不通过简单整体放大表达升级；
- 三个等级应保持同一塔种的识别核心；
- 分支升级未来通过顶部模块、弹道形状和底座徽记表达。

### 7.3 建造台状态

| 状态 | 表现 |
|---|---|
| 空闲 | 低亮度底座和编号/微型图标 |
| 可建造 | 暖白边缘呼吸，显示成本 |
| 选中 | 对应塔种功能色边缘 + 半透明预览 |
| 不可建造 | 降饱和，成本数字变红，不闪烁 |
| 可升级 | 小型上箭头或扳手标记，不遮挡塔体 |

## 8. 敌人与 Boss

### 8.1 模块化身体系统【已定】

首轮使用三个基础身体：

| 身体 | 轮廓与步态 | 可派生敌人 |
|---|---|---|
| 普通体 | 中等体型、拖步、前伸手臂 | 行尸、裂变、尖啸、再生 |
| 快速体 | 瘦小、强前倾、高步频 | 疾行、爆裂、潜行 |
| 重装体 | 宽肩、低重心、慢步幅 | 重装、装甲、攻城 |

行为通过头部、背部、胸腹、手臂和携带物覆盖件派生：

- 裂变：背部/腹部双囊，死亡前短暂鼓动；
- 尖啸：夸张下颌或背负扩音感染器；
- 爆裂：橙红感染囊，接近死亡时脉冲加快；
- 装甲：不对称钢板和头盔，正面轮廓更方；
- 再生：毒绿菌簇/管线，回血时从暗到亮；
- 潜行：低伏轮廓、披布、地面尘线；
- 攻城：巨臂、混凝土块或墙锤式覆盖件。

### 8.2 威胁等级语法【已定】

- 普通敌人：不使用常驻地环；
- 特殊敌人：一个明显轮廓件 + 一个行为提示；
- 精英：更大体量、专属底部标记、入场短标签；
- Boss：独有轮廓、环境压暗、顶部长血条、低频冲击波；
- 高威胁单位必须在被塔和特效部分遮挡时仍可辨认。

### 8.3 Boss 轮廓方向【工作标准】

| Boss | 轮廓方向 | 入场特征 |
|---|---|---|
| 冲锋领主 | 前倾、巨大肩甲/撞角、长腿 | 道路直线警示，短促蓄力 |
| 巢穴领主 | 背部巢囊、多个附肢或拖曳小尸 | 巢囊搏动，小尸影子先出现 |
| 壁垒领主 | 极宽、低重心、层叠装甲 | 炮击火花被弹开，沉重脚步 |
| 尸潮君王 | 高大直立、冠状感染结构、长臂 | 全场压暗，尸群短暂停步后推进 |

### 8.4 血腥程度【工作标准】

- 允许污渍、碎屑、破布、感染液和夸张倒地；
- 不表现写实内脏、断肢特写或持续血泊；
- 死亡效果以缩扁、翻倒、消散、感染烟和掉落物为主；
- 爆裂类可以有橙绿感染液，但避免接近真实血液表现。

## 9. 动画与运动语言

### 9.1 总原则【已定】

- 状态变化必须快于装饰动画；
- 先保证起点、终点和受力方向正确，再增加细节；
- 小幅程序动画优先于大量逐帧动画；
- 高频事件短而克制，低频事件可以更有仪式感；
- 动画不得推迟输入响应或影响确定性模拟。

### 9.2 建议时长【工作标准】

| 事件 | 时长 | 动作 |
|---|---:|---|
| 按钮按下 | 70～100ms | 缩放至 0.96，快速回弹 |
| 建造落地 | 240～320ms | 下落、轻弹、尘圈、短高光 |
| 塔升级 | 350～500ms | 部件展开/替换、环形光、等级标记 |
| 机枪后坐 | 70～110ms | 枪管后移并回位 |
| 火炮后坐 | 160～240ms | 大幅后坐、底座轻震 |
| 普通受击 | 80～140ms | 白闪、挤压、轻后仰 |
| 普通死亡 | 260～420ms | 翻倒/缩扁/消散 |
| 精英入场 | 500～700ms | 地环、短标签、体型强调 |
| Boss 入场 | 900～1400ms | 环境压暗、血条、冲击波 |
| 资源飞向 HUD | 350～550ms | 曲线移动、终点吸附和数值跳动 |

推荐 Phaser 缓动：

- UI：`Sine.easeOut`、`Back.easeOut`；
- 建造与升级：`Back.easeOut`；
- 弹道：`Cubic.easeOut` 或线性；
- 受击与震动：快速 `Quad.easeOut`；
- 资源吸附：`Cubic.easeIn`。

### 9.3 屏幕震动【工作标准】

- 普通射击不震屏；
- 炮击命中：2～4px、60～100ms；
- 城墙重击：3～5px、80～140ms；
- Boss 入场/死亡：6～10px、150～220ms；
- 同一时间只响应最高优先级震动；
- 提供“降低动态效果”后，震幅和时长至少减半。

## 10. VFX 与战斗可读性

### 10.1 VFX 优先级【已定】

从高到低：

1. 城墙危险、Boss 技能与失败风险；
2. 玩家当前选择和可交互状态；
3. 四种塔的攻击与异常状态；
4. 资源、经验和普通伤害数字；
5. 环境火星、雾、灰尘等装饰效果。

高优先级出现时，应主动压低或隐藏低优先级效果。

### 10.2 四种攻击的固定语法【已定】

- 机枪：细、直、短寿命黄白线；
- 火炮：可追踪抛射物 + 橙红圆形爆炸 + 地面余烟；
- 冰冻：青蓝扇形/冰片 + 敌人霜层 + 降饱和；
- 电磁：白色核心、紫色外辉的折线 + 清楚的跳跃顺序。

### 10.3 通用事件

| 事件 | 表现 |
|---|---|
| 开波 | 入口脉冲、红色扫光、短标题，不遮挡操作超过 0.8 秒 |
| 攻墙 | 墙体局部白闪、碎屑、裂纹变化、耐久条跳动 |
| 精英出现 | 专属形状地环和名称短标签 |
| Boss 出现 | 环境压暗、顶部血条、低频冲击波 |
| 击杀 | 敌人动作 + 小型资源/经验释放，不为每只怪放大爆炸 |
| 强化生效 | 从卡片向受益对象输送一条能量流 |
| 胜利 | 尸潮停止、暖光提升、残余火星向上 |
| 失败 | 墙体破口、暖光熄灭、敌群越过防线 |

### 10.4 屏幕噪声限制【工作标准】

- 同屏飘字建议最多 8～12 个，密集伤害合并或降低显示频率；
- 普通敌人血条在满血时可隐藏，受伤后显示；
- 地面范围提示必须位于单位与弹道下方；
- 装饰粒子透明度低于战斗粒子；
- 强光面积不得长期覆盖道路宽度的 30% 以上；
- 任何 VFX 都不能掩盖城墙耐久和 Boss 技能预警。

## 11. UI、文字与图标

本章只定义与整体美术一致的高层视觉原则。主战场布局、组件尺寸、交互状态、商店、3 秒倒计时、响应式和工程边界，以 [ZCamp UI Bible](../ui/ZCamp_UI_Bible.md) 为准，避免两份文档重复维护。

### 11.1 信息层级【已定】

#### 一级：始终可见

- 波次/阶段；
- 城墙耐久；
- 木材、金币；
- 当前战斗、商店或 3 秒开波倒计时状态。

#### 二级：情境可见

- 塔的成本、等级、升级；
- 经验与下一次强化进度；
- 精英/Boss 信息；
- 维修与挑战状态。

#### 三级：展开后可见

- 详细塔属性；
- 强化历史；
- 长说明；
- 重新开始和设置。

### 11.2 HUD【工作标准】

- 顶部采用少量图标 + 短数字，不使用整句说明；
- 城墙耐久应是最显眼的状态条，但健康时保持克制；
- 波次显示建议采用 `第 3/20 波` 或 `3 / 20`；
- 开发标记、引擎版本和测试文字不得出现在玩家画面；
- 暂停放在顶部角落；重开只在暂停菜单或结算中出现。

### 11.3 底部四卡手牌【工作标准】

- 四种塔始终按机枪、火炮、冰冻、电磁固定排序；
- 参考《皇室战争》的表现结构：四张竖向卡横排，成本徽记置于卡片左上，图标是最大信息，名称位于底部；
- 借鉴的是成本徽记与卡片角部绑定的稳定关系，不强求复制其具体角位；ZCamp 首版统一置于左上，真机测试后只允许四卡整套迁移；
- 四张卡默认共用中性深色卡壳；塔种功能色集中在插画、角标和选中内辉，不做四种常驻彩色外框；
- 当前选中卡上抬 6～10px，使用暖白外轮廓 + 对应塔种功能色内辉；其他卡不缩小、不换位；
- 横向木材资源轨道位于格区和手牌之间，作为两区分界；左端显示木材图标与真实当前值；
- 每张卡的成本徽记包含木材小图标 + 数字，让资源与消费无需推理即可对应；
- 资源轨道不照搬紫色分段圣水条；填充只有在玩法定义真实容量上限时才表达比例，否则作为非比例状态带；
- 选中后只突出一张卡和 15 个合法建造格；不可支付的卡整体降亮，但成本仍可读；
- 只借鉴卡牌布局与按压反馈，不引入循环卡组、下一张预览或圣水机制，除非玩法另行定义；
- 主战场不显示“开始战斗”或“开始下一波”按钮；
- 维修是情境操作，城墙健康时降低视觉权重。

### 11.4 强化三选一【工作标准】

每张卡只呈现：

1. 一个清晰图标；
2. 2～6 字标题；
3. 一句效果，核心数值加粗或着色；
4. 受益对象的固定功能色；
5. 稀有度或类别边框（如未来需要）。

不要在卡片上重复规则背景，不要使用超过三行的说明文字。

### 11.5 字体与字号【工作标准】

首轮字体栈：`"Noto Sans SC", "Microsoft YaHei", system-ui, sans-serif`。

| 用途 | 建议字号 | 字重 |
|---|---:|---:|
| 游戏标题/结算标题 | 32～40px | 700～900 |
| 大数值/Boss 名称 | 26～32px | 700 |
| 主 CTA/区域标题 | 22～26px | 700 |
| HUD 与卡片标题 | 18～22px | 600～700 |
| 正文 | 16～18px | 400～500 |
| 次级标签 | 14～16px | 400～500 |

关键数字使用等宽数字特性或固定宽度容器，避免资源增长时 HUD 左右跳动。

### 11.6 图标规则【已定】

- 采用实心大形状 + 少量内部切口；
- 24px 时仍能辨认；
- 同组图标统一视角、描边粗细和光源；
- 木材、金币、城墙、波次、等级分别使用不同轮廓；
- 不以颜色作为图标的唯一含义；
- 升级图标优先表现“对象 + 变化”，而不是抽象星光。

### 11.7 触控与状态

- 主要触控目标建议不小于 56×56 逻辑像素；
- 按钮必须有默认、按下、不可用、选中状态；
- 不可用状态应说明原因，例如资源不足，而不是完全消失；
- 战斗中的高频按钮应位于下半屏可触达区域；
- 所有输入反馈应在 100ms 内开始出现。

## 13. 资产制作与技术规格

### 13.1 制作方式【工作标准】

- 主战场 UI 以已确认 D3 SVG 为矢量母版；布局、色彩和组件比例从母版派生，不在代码中凭感觉重画；
- UI、建筑和静态对象优先使用分层矢量源文件，运行时按目标尺寸导出 PNG/WebP 或图集；
- 可用简单 3D 模型辅助统一视角，但最终必须收敛为 D3 的粗轮廓、大块面和两档明暗；
- 小型循环动画优先使用分层部件 + Phaser Tween；
- 只有招牌事件才使用逐帧序列；
- 背景使用 WebP；需要透明度的精灵、UI 和 VFX 使用 PNG/WebP Alpha；
- 多帧单位和 VFX 使用 Texture Atlas。

### 13.2 工作分辨率

- 逻辑画布：720×1280；
- 美术源文件建议按 2×，即 1440×2560 对照制作；
- 导入后在 Phaser 中按逻辑尺寸显示；
- 关键单位在最终显示尺寸下检查，不以放大图判断细节；
- 同类资产使用相同的画布、地面接触点和阴影范围。

### 13.3 锚点

- 地面单位：脚底中心；
- 建筑和塔：底座中心；
- 弹道：几何中心或弹头位置；
- 爆炸/地面特效：范围中心；
- UI 图标：视觉中心，不以透明画布中心代替；
- 血条和状态标记通过统一挂点配置，不手工逐只偏移。

### 13.4 命名规范【已定】

统一使用小写蛇形命名：

```text
env_road_straight_01.webp
env_wall_damage_02.png
tower_machine_gun_l1_base.png
tower_machine_gun_l1_barrel.png
enemy_runner_idle_00.png
enemy_runner_overlay_volatile.png
boss_overlord_intro_00.png
vfx_cannon_impact_00.png
ui_icon_resource_wood.png
ui_card_upgrade_damage.png
```

建议前缀：`env_`、`tower_`、`enemy_`、`boss_`、`vfx_`、`ui_`、`icon_`、`logo_`。

### 13.5 图集与导出【工作标准】

- 单张图集建议不超过 2048×2048；
- 图集边缘保留 2～4px extrusion/bleed，避免缩放采样出血；
- 删除无意义的大面积透明边缘；
- 颜色空间统一为 sRGB；
- 同一动画帧保持一致画布和锚点；
- 背景按视觉层拆分，避免每次场景变化导出整张大图；
- 资产进入仓库前必须在 Chrome/移动端缩放下检查一次透明边与锐度。

### 13.6 内部性能预算【工作标准】

以下是项目内部目标，不等同于任何平台官方限制：

- 首屏必需美术资源传输体积目标：不超过 4MB；
- 完整 MVP 美术资源目标：不超过 12MB，非首屏内容可延迟加载；
- 战斗常驻纹理显存目标：不超过约 64MB；
- 常规战斗粒子建议不超过 120 个活跃对象；
- 常规战斗渲染批次/Draw Calls 目标：尽量低于 80；
- 不为每一波生成独立背景或独立敌人整套纹理；
- 先通过合图、复用和对象池解决问题，再降低关键资产清晰度。

所有预算需在第一批真实资产接入后用目标设备实测修订。

## 15. 可读性、无障碍与舒适度

### 15.1 可读性规则【已定】

- 敌人、塔和交互状态必须至少用“颜色 + 形状/动作”双重编码；
- 重要文本与背景保持足够对比，并在复杂场景上使用底板或描边；
- 小字号不承载关键玩法信息；
- 快速敌人靠步频和前倾轮廓识别，重装敌人靠体量和步态识别；
- Boss 技能预警使用形状、节奏和位置，不只使用红绿变化。

### 15.2 动态舒适度

- 设置中预留“降低屏幕震动”和“降低闪烁”选项；
- 高频闪烁避免超过每秒 3 次；
- 全屏白闪透明度和持续时间保持克制；
- 强化卡出现时不持续缩放或漂浮；
- 大量敌人同时死亡时合并反馈。

## 16. 视觉验收标准

每个玩家可见改动至少通过以下相关检查。

### 16.1 五秒截图测试

向未参与开发的人展示战斗截图五秒，对方应能回答：

- 哪边是玩家营地；
- 敌人从哪里来；
- 哪个目标不能被攻破；
- 至少两种塔有什么不同；
- 当前最紧急的信息是什么。

### 16.2 手机尺寸测试

- 在 720×1280 逻辑尺寸下无裁切；
- 在较矮竖屏和较长竖屏下关键 UI 不重叠；
- 将截图缩小到约 360px 宽时，塔、普通敌人、重装敌人和 Boss 仍可区分；
- 最小正文和关键数字可读；
- 所有主要按钮可触达且状态清楚。

### 16.3 战斗噪声测试

- 三种以上塔同时攻击时仍能追踪 Boss 和城墙状态；
- 10 个以上敌人出现时，路线和高威胁敌人仍清晰；
- 飘字不会覆盖强化选择或主要按钮；
- 炮击、冰冻和电弧不会被误认为同一类攻击；
- 关闭特效后，玩法状态仍能由单位和 UI 读懂。

### 16.4 商品化截图测试

- 画面中没有引擎版本、测试标记、占位文字或开发按钮；
- 不依赖说明文字也能看出“营地防守尸潮”；
- 至少有一个暖色情感中心和一个明显威胁方向；
- 截图裁切后仍有清晰焦点；
- 所见必须来自真实运行画面。

### 16.5 技术验证

- `npm run check` 通过；
- `npm run build` 通过；
- 浏览器控制台无新增资源加载错误；
- 对玩家可见的布局和动画改动提供可复现截图或视觉检查记录；
- 核心模拟不依赖 Phaser、DOM 或美术资源状态。
