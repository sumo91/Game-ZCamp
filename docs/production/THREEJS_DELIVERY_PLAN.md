## 分支与工作树

- 主交付分支：codex/threejs-integration，基于当前本地 master 及已提交规格，保持包含 origin/master 的已确认内容。
- 每个代码子任务使用独立工作树和 codex/threejs-issue-N 分支，从当时最新的集成分支创建。优先使用 Codex 管理的工作树，保留用户工作区。
- 完成子任务前先合并最新集成分支，再运行对应检查。不要重置用户未提交内容。
- 合入以 merge commit 保留子任务来源及可追溯提交。避免让多个实施代理修改同一个工作树。
- 提交只包含本任务修改。提交信息引用 Issue；证据文件随对应任务提交。测试失败的 red 阶段保留日志证据，不把不能通过回归的状态当作可合入交付。
- 不覆盖远端历史，不直接将未验收迁移推入 master。回退使用可追溯的修复或撤销提交。

## 实施、审查与推送

采用 implement-spec：实施子代理按任务独立工作树工作；合入由独立合入代理完成；代码审查分别检查项目标准与对应规格。

1. 根会话读取规格、全部子任务与原生依赖，选择阻塞任务已完成的下一项。当前首先实施 #2。
2. 实施代理使用 tdd，按规格已确认的核心 GameCommand/GameState/GameEvent、高层战斗会话及浏览器玩家流程验证，先观察新行为失败，再实现通过；不重新建立大量私有模型测试。
3. 每项完成后提交实现、相关测试及证据，报告提交 SHA、验证命令、运行入口和已知限制。
4. 审查该项与合入后集成差异，修复实质问题；运行 npm run check、npm run build，以及对应浏览器/资产/性能验收。
5. 合入代理将通过检查的子任务合入集成分支。根会话核对提交与工作区，推送子任务和集成分支至 origin，并核对远端 SHA。
6. 首个代码任务合入后创建面向 master 的整体 Draft PR，附实施进度及证据，并关联 #1 和所有子任务。之后随着交付更新同一 PR。
7. 普通子任务在达到验收标准、合入集成分支、推送及证据记录完成后关闭，注明目前交付所在分支与提交。PR 中保留任务完成记录。
8. #13 接受及完整集成审查通过后，将整体 PR 转为可审查并采用 merge commit 合入 master；尊重届时远端分支规则和检查。验证 origin/master 包含交付提交，再完成 #1。
9. 归档已交付且无所需未保存资源的 Codex 工作树，保留 PR、Git 提交、源资产和证据的恢复路径。

首个代码任务同时补齐用于 PR 的自动检查（类型、测试、构建），使用仓库可支持的 Node.js 版本与官方 GitHub Actions。分支保护配置的变更需要另行明确指示；现有规则不由该流程自动改写。
