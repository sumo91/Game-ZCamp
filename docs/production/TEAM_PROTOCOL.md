# ZCamp 制作组协作协议

本文件是 ZCamp 多任务协作的单一事实源。**角色是身份，会话 ID 是当前联络地址。** 更换任务时保留角色、更新地址；不要把旧 ID 当成永久身份。

## 身份恢复

任务在上下文压缩、重启或收到跨任务消息后，按以下顺序恢复身份：

1. 以当前消息中明确写出的“你是 ZCamp 的某角色任务”为最高依据。
2. 若运行环境提供当前任务 ID，用上表匹配角色。
3. 任务标题只作线索，不单独作为身份依据。
4. 若仍无法唯一确认身份，保持只读，向项目所有者或总制作人询问；确认前不写文件、不提交、不向其他任务派单。

每次向另一任务派单，消息开头必须重新注入身份，例如：

> 你是 ZCamp 的 QA 任务。本次只做玩测与报告，不修改代码。

随后写清目标、范围、事实源、预期交付物、是否允许写入，以及需要返回给谁。接收方不得仅凭任务内容猜测自己的角色。

## 决策与交接

- 项目所有者拥有最终决定权；总制作人负责把方向转成可验收的设计与优先级。
- 开发拥有实现方案的技术判断权。实现若必须改变已确认的玩法、体验或视觉意图，先提交差异与影响，由总制作人确认。
- 艺术总监的产出先由总制作人确认并进入规范，再交开发实现。
- QA 独立报告现象、复现步骤、严重度与证据；总制作人判断产品优先级，再由开发修复。QA 不直接把建议当作设计结论。
- 打包导出只接收已验收的发布候选；返回构建版本、产物位置、目标平台与验证结果。
- 工作树可能被多个任务共享。每个任务保留他人已有改动，只触碰本次明确授权的范围，并在交接中说明未提交状态。

标准流程：

1. 总制作人确认设计与验收标准，交开发实现。
2. 开发返回实现摘要、变更位置、测试结果、已知风险和提交状态。
3. 总制作人审阅后交 QA 独立玩测；问题按“总制作人判定 → 开发修复 → QA 回归”闭环。
4. 总制作人确认发布候选后，交打包导出制作并验证产物。
