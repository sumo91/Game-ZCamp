# Mission Brief: 从营地主界面选择配置并由首名英雄参与十波战斗

## Outcome

玩家启动游戏后先进入可扩展的营地主界面，能够看见当前关卡、当前英雄与尚未开放的神器养成位，并通过明确的“开始战斗”进入现有十波关卡。战斗中原固定主城位置由首名英雄“营地守望者”驻守；英雄以基础攻击参与防守，并通过木材产量与独立城墙护盾改变本局玩法。战斗结束后玩家可以再战或返回营地。

## Context

- 目标仓库为 ZCamp Phaser 竖屏网页游戏，实施基线是 `master` 的 `b24276245fba21ab7fa0428f0a2519d18aceabf4`；功能分支为 `codex/lobby-hero-foundation`。
- 当前启动入口直接创建 `GameScene`；现有战斗规则、前三波缓和节奏、建筑成长/改造与十波胜负均已作为正式基线。
- 长期事实源包括 `docs/尸潮营地_建筑成长改造_阶段版本设计_v0.2.md`、`docs/ui/ZCamp_UI_Bible.md`、`docs/art/ZCamp_Art_Bible.md` 与 `docs/production/TEAM_PROTOCOL.md`。本 Brief 只补充新阶段委托，不重写既有战斗规则。
- 《皇室战争》截图只提供“中央关卡、底部配置、主要战斗按钮”的信息层级参考，不授权复制其蓝色商业化视觉、品牌元素或外围系统。ZCamp 继续使用现有军用绿、木材、黄铜、战地面板与竖屏气质。

## Required Behaviors

- 游戏启动后不得自动进入战斗。营地主界面至少清楚呈现一个当前场地、当前英雄“营地守望者”、一个标明“神器/养成尚未开放”的非交互占位，以及主要“开始战斗”入口；只有一个选项时不伪装成已有多关卡、多英雄或可用套组。
- 营地主界面不得展示木材、金币等局内资源，也不得引入商店、通行证、排行榜、抽卡或永久货币。玩家点击关卡或英雄可查看足以理解当前配置的详情，但不会进入无内容的假选择流程。
- “开始战斗”以当前关卡和英雄配置创建一局全新、确定性的十波战斗。配置边界应能自然扩展到后续多关卡、多英雄和神器，但本阶段只提供一个合法关卡与一个合法英雄。
- 当前固定主城格在玩家可见语义上改为英雄驻守位：英雄固定在该位置，不占普通建筑名额，不可拆除、建造、升级或改造成塔，也不是敌人攻击和战败判定目标；城墙仍是唯一失败目标。
- “营地守望者”拥有与 Lv.1 箭塔相同的基础攻击档案与确定性索敌行为，自动按频次攻击敌人。该能力称为“基础攻击”，不是需要玩家点击的主动技能；本阶段不显示或实现可点击主动技能按钮。
- 英雄核心被动使本局所有木材产量的最终结果乘以 `1.10`，包括基础产量与木材厂产量。显示值和实际结算必须来自同一 core selector，暂停、词条选择、系统暂停及终局期间仍不产出。
- 每局开局获得独立的 `100` 点城墙护盾。敌方对城墙造成的伤害先消耗护盾，再伤害原有 `100` 点城墙生命；护盾不可维修、不会被普通修复效果恢复，每次新局或重开重新初始化。界面以不同形状/文字和独立读数区分护盾与城墙，不只依赖颜色。
- 英雄详情在营地主界面和战斗中均能让玩家理解“基础攻击、木材总产量 +10%、开局护盾 +100”，不得把自动攻击文案包装成可主动释放的技能。
- 现有建造、升级、改造、词条三选一、战术暂停、开局倒计时、敌人、波次、Boss、资源价格和终局规则保持不变。英雄加入后若体感难度变化，只记录为后续平衡输入，不在本委托内顺带重调波次数值。
- 胜利与失败界面同时提供“再战”和“返回营地”。再战使用同一配置创建干净新局；返回营地不得残留上一局敌人、资源、护盾、建筑、词条、计时或暂停状态。
- 720×1280 与 360×640 下，营地主界面、英雄详情、Battle 入口、战斗 HUD、双层耐久显示和终局返回入口均完整可读可点，无裁切、重叠或点击穿透。

## Constraints

- 模拟、英雄配置、基础攻击、木材乘区、护盾结算和战斗初始化属于 `src/core`，必须确定性、平台无关且可独立测试；Phaser、DOM、墙钟和浏览器状态不得进入 core。
- 新关卡与英雄采用 typed、data-first 定义和校验，不把名称、倍率、护盾值或攻击档案散写在场景逻辑与多个 UI 分支中。
- Phaser 负责场景切换、绘制、动效、点击与可见反馈；玩家可见数值来自 core 状态或纯派生 view model。
- 保留现有 5×3 格位与固定中央驻守位置，不通过删除可建格、移动城墙或改变战场比例为新界面腾空间。
- 保持现有触屏输入优先级、战术暂停冻结、结果锁定、浏览器缩放和 GitHub Pages 路径兼容。
- 实施期间不得合并 `master`、推送 `master` 或发布 GitHub Pages；只有项目所有者试玩确认后才可发布。

## Non-goals

- 多关卡内容、关卡解锁或地图进度。
- 多英雄选择、英雄升级、品质、等级、装备或养成数值。
- 神器的获得、套组编辑、持久化或战斗效果。
- 可点击的英雄主动技能、技能能量、冷却按钮或手动瞄准。
- 大厅商店、账号、社交、赛季、排行榜、通行证、广告、付费或云存档。
- 因英雄战斗力而重新平衡波次、塔、资源价格或敌人属性。
- 对现有 Art Bible 进行全面视觉重制。

## Evidence of Completion

- 自动化从 core 边界证明：合法关卡/英雄配置与拒绝无效引用；木材最终乘区同时影响显示与结算；护盾先于城墙承伤且不可修复；英雄攻击档案、索敌和暂停行为确定；重开与返回后的新局状态无泄漏；原十波、成长和改造回归仍通过。
- 纯 UI/输入测试证明营地配置、主按钮、占位状态、英雄详情、双层耐久、终局双入口及模态优先级不依赖场景散写数值。
- 真实浏览器从首次加载完成“营地 → 查看关卡/英雄 → Battle → 首波中英雄攻击与护盾承伤 → 战术暂停 → 终局入口或可控结果路径 → 返回营地/再战”的代表性流程；不得以直接注入运行时状态代替主流程证据，耗时过长的十波终局可由确定性 core 测试补足。
- 720×1280 与 360×640 均有可复核截图或同等视觉证据，console `error/warn` 为空，静态资源无 404；构建、类型检查、测试与 `git diff --check` 通过。
- 交付报告列出变更边界、测试结果、浏览器覆盖、已知平衡风险、提交与远端功能分支状态，并明确 `master`/Pages 未被触碰。

## Delegated Decisions and Unknowns

- 开发拥有场景拆分、配置对象接口、英雄状态表示、事件名称、纯 view model 与测试 seam 的实现判断权；优先复用现有深模块和单一事实源，不为唯一内容建立大而空的框架。
- 营地主界面的具体关卡名、副标题、图形构图、英雄头像和轻量转场可在既有 UI/Art Bible 内决定；信息层级必须清楚，视觉不能直接仿制参考截图。
- 英雄基础攻击可复用箭塔攻击档案或由共享档案引用，选择能防止两者后续数值漂移的方式；玩家观察到的当前结果必须等同于 Lv.1 箭塔。
- 护盾在 HUD 中的具体排布、条形方向与受击反馈由开发决定，但必须与城墙分层可读，并为未来其他英雄护盾值留出内容定义入口。
- 若现有“主城”内部结构不能在不破坏存档或测试的情况下直接更名，可保留迁移适配层；玩家可见内容和新领域语言不得继续把英雄显示为主城。

## Autonomy and Approval Boundaries

- 授权在功能分支内进行必要的源码、测试、设计/UI 文档与本地证据修改，运行本地服务、构建和自动化，提交并推送功能分支。
- 授权删除仅被本阶段明确替代、且已由搜索证明无其他消费者的旧主城展示代码；保留历史文档和证据。
- 任何波次、敌人、塔、费用、升级、改造、词条或既有视觉规范的变化，以及新增持久化、外部服务、素材采购或范围内没有定义的元系统，都需要先向总制作人报告差异并等待确认。
- 合并或推送 `master`、发布 GitHub Pages、删除远端分支或执行不可逆外部操作必须由项目所有者另行确认。
