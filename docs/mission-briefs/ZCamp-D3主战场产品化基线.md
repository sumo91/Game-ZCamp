# Mission Brief: D3 主战场成为可玩的产品化基线

## Outcome

当前 ZCamp 运行版本的主战场被替换为一套与已确认 D3 母版一致、可真实交互和可继续扩展的竖屏产品界面。玩家进入游戏后，能够在清楚的 5×3 营地中使用四张防御塔卡完成建造与升级，经过波间整备和确定性的 3 秒倒计时进入自动战斗，并始终读懂尸潮方向、城墙风险、波次、资源与当前操作状态。

这次交付完成的是主战场的产品化骨架与阶段流，不是静态复刻效果图。已有战斗规则和内容继续真实运行，界面不再呈现开发按钮、调试文字或 5×2 原型布局。

## Context

- 目标环境为 Phaser 4、TypeScript、Vite，720×1280 竖屏，面向移动端与小程序。
- 视觉与空间母版：[D3 SVG](../ui/visuals/zcamp-battle-ui-d3-vector.svg)；稳定坐标、区域、格位和卡牌接口见[开发与扩展说明](../ui/visuals/README.md)。
- 界面与交互权威规范：[ZCamp UI Bible v0.7](../ui/ZCamp_UI_Bible.md)。
- 气质、色彩、造型与动效权威规范：[ZCamp Art Bible v0.10](../art/ZCamp_Art_Bible.md)。
- 玩法上位规范：[《尸潮营地》MVP 产品概述](../尸潮营地_MVP产品概述.md)。
- 当前实现仍存在 UI Bible 第 18 章列出的原型债务，包括 5×2 格、手动开波、大型文字按钮、多行开发 HUD，以及缺少核心 `SHOP` / `COUNTDOWN` 状态。

当示意画面与文字规范冲突时，D3 决定空间比例、造型语言和组件视觉关系，UI Bible 决定信息架构与交互，产品概述决定玩法语义。不得因当前原型更容易保留而反向修改这些基线。

## Required Behaviors

- 运行画面遵守 D3 的纵向语义顺序和基准区域：尸潮战区、嵌墙耐久、固定 5×3 营地、木材轨道、四卡手牌；15 个格位拥有稳定且可测试的 `slot-r{row}-c{column}` 身份。
- 尸潮区保持绝对视觉主体。HUD 叠加在战场，不切出永久顶部横栏；金币位于左上，波次与剩余敌人位于上中，暂停位于右上，城墙耐久只嵌在墙体，木材及其建造语义只在底部资源轨道表达。
- D3 左上三块纵向信息板仅是旧示意内容，不作为 HUD 排列规则。玩家画面不得出现标题、Phaser 版本、`SETUP READY`、操作说明长句或主战场开波按钮。
- 新局从初始 `SHOP` 开始；敌人清空后自动返回波间 `SHOP`。玩家选择“完成整备”后进入不可重复确认的 3 秒 `COUNTDOWN`，随后自动进入 `COMBAT`。暂停、后台恢复、重开和状态切换不得跳秒、重复开波或产生非确定结果。
- `COUNTDOWN` 期间保留战场、营地与手牌的空间记忆，但建造和升级输入不可用；`COMBAT` 与 `SHOP` 中保留现有防御塔建造和升级能力。
- 底部四卡在本次交付中固定为机枪、火炮、冰冻、电磁四种防御塔，内容顺序、名称、成本、图标和功能色来自类型化内容数据。主城、伐木场、修理所及其入口属于后续经济闭环任务；D3 中出现的这些建筑是布局与视觉示例，不得在本次用无规则的假按钮冒充完成。
- MVP 主输入为“点卡 → 点格”。选择后 15 格明确显示合法、非法、占用和目标状态；资源不足或命令被拒绝时说明具体原因，且同一输入只会触发一次消费。拖放不是本次完成条件。
- 点击已占用格应进入可读的建筑详情/升级状态，不得因一次普通点击直接消费升级资源。战斗中不提供拆除、换位或售卖。
- 木材当前没有已批准的容量上限，因此资源轨道不得显示伪造的百分比填充。它应显示真实木材值，并可用非比例的获得脉冲、飞入或数值跳动反馈变化。
- 已有自动战斗、四塔差异、敌人、波次、强化、城墙胜负、暂停与重开能力不能因界面换代而退化。核心拒绝原因和显示内容保持数据驱动，Phaser 只翻译输入与表现状态。
- 商店、倒计时、强化、暂停和结算遮罩出现时，背景输入被正确阻断；任何战斗特效不得覆盖 HUD、城墙耐久和四卡操作层。

## Constraints

- 游戏规则、15 格、阶段状态、倒计时和命令结果属于 `src/core`，保持固定步长、确定性和平台无关；Phaser、DOM、Tween、系统墙钟及资源加载状态不得成为规则依据。
- 玩家可见内容遵守 Art Bible 的块面卡通、粗外轮廓、两档明暗、大头短肢、低材质噪声与固定四塔功能色；不得回退为彩色圆形、开发面板或暗黑写实风格。
- D3 SVG 是母版和资产来源，不得作为一张覆盖全屏的不可交互背景图。运行时各区域、对象、状态和热区必须保持独立。
- 内容继续数据优先。新增或调整卡牌、成本、图标键、拒绝原因和布局身份时使用类型化定义与校验，不在场景代码中散写内容规则。
- 主要触控热区至少 56×56 逻辑像素；重要状态不得仅靠颜色表达；主要输入反馈须在 100ms 内开始。
- 保留用户和艺术总监现有的未提交文档，不重写、删除或回退与本任务无关的工作区变更。

## Non-goals

- 完整伐木场、修理所、主城、金币强化商店或挑战任务系统；
- 四塔 Lv.2/Lv.3 的正式美术资产、其余 Boss、完整敌人资产和最终 VFX 图集；
- 拖放建造、拆除、换位、售卖、横屏布局或局外成长；
- 20 波最终数值平衡与 10～15 分钟完整通关调优；
- 用临时假交互宣称上述系统已经完成。

## Evidence of Completion

- 核心自动化证据覆盖：15 个稳定格位；`SHOP → COUNTDOWN → COMBAT → SHOP`；完整 3 秒推进；暂停/恢复；重开；重复输入不重复消费；倒计时期间拒绝建造；背景弹层输入阻断。
- 一次从新局进入初始商店、建塔、完成整备、自动倒计时、完成第 1 波并回到商店的可复现真实浏览器运行记录。
- 720×1280 与约 360px 宽的玩家画面截图，能够通过 UI Bible 的五秒识别、布局和商品化截图检查；至少额外提供一张卡牌选中/合法格状态截图。
- 截图中不存在手动开波按钮、开发标记、5×2 网格、伪木材容量条或被特效遮挡的关键 UI。
- `npm run check`、`npm run build` 和浏览器控制台检查通过，无新增资源加载错误；相关玩家可见改动有可定位的截图或录屏证据。
- 交付报告明确列出仍属于后续任务的经济建筑、正式资产与平衡缺口，不把视觉示例或占位状态计为功能完成。

## Delegated Decisions and Unknowns

- 可以自行决定显示对象、容器、布局常量、资源导出和测试组织方式，只要 D3 稳定接口、核心边界和玩家可见结果不漂移。
- 商店面板在上方尸潮区中的具体排版、建筑详情的具体展开方式、合法格的克制动效可以结合现有架构决定；优先保证单手操作、战场空间记忆与低噪声。
- 若 D3 中的矢量符号不适合直接进入运行时，可选择独立导出或程序重建，但必须保持母版轮廓、颜色和目标尺寸，并说明资产来源与后续替换点。
- 当前正式中文字体和设备首包约束尚未最终锁定。首版可以使用 Bible 指定字体栈与现有安全加载方式，不得因此阻塞布局交付。
- 如果现有核心规则与本任务的已定状态流发生结构冲突，应保持本任务 Outcome 与 Constraints，报告冲突和迁移影响，不得静默用 Phaser 本地状态模拟通过。

## Autonomy and Approval Boundaries

- 允许在当前仓库中进行完成本任务所需的本地、可逆代码、测试、资源导出和文档证据变更，并运行项目既有检查、构建与本地浏览器验证。
- 不得提交、推送、发布、部署、安装新的外部依赖、删除用户文件、重写艺术或产品基线，除非用户或总制作人另行明确授权。
- 不得自行扩大到 Non-goals。发现需要产品判断的矛盾时，先向总制作人报告，不向艺术总监任务追问或打断其工作。

## Execution Directive

You own delivery of the outcome above. Investigate the relevant environment, choose an efficient path consistent with its existing conventions, make the in-scope changes, and validate the result with evidence appropriate to the task.

Adapt the route as evidence appears. Preserve the Outcome and Constraints when assumptions conflict with repository facts, and report material divergence. Resolve discoverable implementation questions yourself; escalate only decisions requiring user judgment or approval.

Continue until the outcome is delivered and credibly verified. Report the result, evidence, and remaining uncertainty.
