# Mission Brief: ZCamp 只保留建筑成长规则并形成可独立验收的候选版

## Outcome

ZCamp 的当前功能分支形成一个可在本地交给项目所有者试玩、可交给 QA 独立回归的阶段候选版：玩家和运行时代码只面对“木材建造/升级、升级触发单建筑词条三选一、金币改造箭塔”的建筑成长循环，不再存在第二套动态卡牌成长规则、运行状态或可操作入口。

## Context

- 项目位于 `D:\00_Ai\Codex\WebGames\ZCamp`，执行分支为 `codex/tower-evolution-v0.2`；阶段 A、B、C 已通过制作人门禁，阶段 C 最终提交为 `a113a64`。
- 角色、权限和交接规则以 `docs/production/TEAM_PROTOCOL.md` 为准。
- 当前玩法事实源与完整验收矩阵是 `docs/尸潮营地_建筑成长改造_阶段版本设计_v0.2.md`，尤其是第 13.4、14、15、16、18 节。
- 阶段 A～C 的任务书与证据保留历史价值，但不得覆盖 v0.2 的当前规则。
- 当前实现仍为过渡结构：新建筑成长循环已成为玩家入口，但核心内容、状态、命令、资源结算、表现派生及测试中仍保留旧卡牌/供牌/弃牌/永久卡/战术卡体系；`docs/ui/ZCamp_UI_Bible.md` 的规范正文仍主要描述旧动态手牌界面。
- 当前公开 `master` 和 GitHub Pages 仍是旧版本；本阶段只制作候选版，不发布。

## Required Behaviors

- 新局的核心状态、合法命令、内容目录和玩家界面只有 v0.2 建筑成长模型。不得保留手牌、下一张牌、供牌计时、满手等待、弃牌、出牌、永久卡应用或战术卡效果等可运行字段与路径，也不得用隐藏 UI 的方式留下第二套可恢复的玩家规则。
- 箭塔、四种特殊塔、木材厂、建筑升级、单建筑词条、木材收入、金币改造、敌人、波次、城墙、暂停和胜负结算继续由单一类型化内容与确定性核心驱动。旧卡牌体系退出后，不能把同一座塔或同一种经济效果留成两份互相漂移的内容定义。
- 金币在当前候选中只有箭塔改造这一条消费路径；木材只有当前 v0.2 允许的建造和升级用途。工程/修理建筑、全局永久强化和战术卡不能从遗留命令、测试注入或内容查询再次生效。
- 核心运行状态不再需要 `legacy_card` 与 `growth` 双模型判别；所有现存建筑均符合当前建筑成长规则。删除旧体系后，现有阶段 A～C 的建造、升级、词条、改造、单建筑隔离、确定性和失败原子性仍成立。
- 当前 UI 不出现“卡牌、手牌、补给、下一张、弃牌、永久卡、战术卡”等旧规则文案或空占位。资源轨、空位建造、建筑详情、升级、改造、拆除和强制词条三选一保持阶段 C 已验收的交互语言与 720×1280、360×640 适配。
- `docs/ui/ZCamp_UI_Bible.md` 升级为当前建筑成长界面的规范事实源：正文明确上下区域结构、资源与费用语言、空位/建筑两类情境面板、升级与改造的区别、强制三选一、暂停与输入优先级、窄屏规则和可用/不可用状态。历史版本记录可以保留旧阶段来历，但任何标为当前或已定的规范不得继续要求动态手牌。
- 60 秒波次、当前尸群数量与确定性脉冲、敌人数值、城墙规则、地图、Boss 与胜负条件保持冻结；战术暂停与强制词条选择的冻结语义不变。

## Constraints

- 遵守仓库 `AGENTS.md`：模拟留在 `src/core`，Phaser/浏览器只做边界适配；玩法内容类型化、数据优先；玩家可见变化必须有可复现自动化或视觉验证。
- 删除旧代码、旧测试与旧规范属于本任务授权范围，但只能在 `codex/tower-evolution-v0.2` 上进行，并须保留他人共享工作树中的无关改动。
- v0.2 冻结数值和规则不得为方便清理而改变。若旧实现与新规则纠缠到必须改变可观察玩法，先报告差异与影响，由总制作人决定。
- UI Bible 的改写必须与现有 UI/Art Bible 视觉基线兼容；本阶段不重新设计整体美术风格，不改 SVG 母版和 Art Bible。
- 不更新 `master`、GitHub Pages 或任何公开发布目标。QA 通过和项目所有者试玩确认之前，功能分支不能被当作正式发布版。

## Non-goals

- 不新增或重平衡敌人、波次、Boss、塔、词条或经济数值。
- 不实现 30 秒初始构筑、90 秒波次、城墙/主城成长、挑战、遗物、局外成长、多难度或词条刷新保底。
- 不制作 APK、原生平台包或公开网页部署。
- 不全面替换美术资产，也不顺带处理既有 bundle 体积提示。

## Evidence of Completion

- 类型检查、全部核心/边界测试和生产构建通过；旧卡牌测试应随旧规则删除，而当前 v0.2 的代表性规则必须继续由有效测试覆盖。测试总数下降本身不构成失败，但不能靠删除测试掩盖新循环回归。
- 代码与当前规范的定向检索证明：运行时源文件、导出接口和现行 UI Bible 规范中不存在旧卡牌内容、状态、命令、供牌、弃牌和可操作文案。历史阶段设计、旧 Mission Brief 与版本历史中的归档文字不计为运行时残留。
- 以相同随机种子和命令序列复验确定性；精确费用/差 1、失败不改变资源与随机状态、强制选择冻结、词条仅作用本建筑、改造只扣金币、木材厂产速只由本建筑贡献等关键边界继续通过。
- 用真实浏览器从新局完整走通 v0.2 第 15.1 节的代表性路径，至少到改造后的特殊塔再次升级并出现本塔专属词条，同时完成一次木材厂升级并验证单建筑隔离；全过程不调用任何旧卡牌入口。
- 在 720×1280 与 360×640 复验资源图标/费用、空位建造、建筑详情、改造弹层、强制词条弹层、不可支付提示、暂停与模态输入；无裁切、重叠、点击穿透或页面自身 console error/warning。保存能够证明最终代码状态的截图与阶段 D evidence 文档。
- 开发交付应包含变更摘要、删除边界、测试/构建结果、浏览器路径、证据路径、提交与推送状态、剩余风险。该交付只成为“QA 候选”；总制作人审阅后另行交 QA 独立玩测，QA 通过后再由项目所有者进行本地候选版试玩与发布判断。

## Delegated Decisions and Unknowns

- 旧卡牌实现与新建筑成长代码的具体拆分、重命名和迁移路线由执行者依据依赖关系决定；优先选择让核心模型更小、规则来源更单一、类型边界更明确的方案，而不是保留兼容层。
- 旧 `ContentCatalog`、旧塔定义、旧表现派生和测试辅助中哪些仍被敌人/波次或当前 UI 合法复用，需要通过调用图确认。保留项必须服务 v0.2 且只有一个权威数据源；仅因“以后可能用到”不构成保留运行时旧规则的理由。
- UI Bible 的章节重排、版本号和历史注记形式由执行者按现有文档约定决定；以当前规范无自相矛盾、可被后续开发直接执行为判断原则。
- 若浏览器长路径需要安全的测试入口或确定性测试辅助，可沿用只在开发/测试环境可用的方式；不得把作弊入口暴露为正式玩家功能，也不得通过篡改运行时状态伪造最终路径证据。

## Autonomy and Approval Boundaries

- 允许在功能分支内读取、编辑、删除旧体系文件与测试，更新 UI Bible 和阶段 D 证据，运行本地服务/自动化/浏览器验证，提交并推送该功能分支。
- 允许为清理旧体系重构内部类型与模块边界，但不得改变已确认的产品规则、数值、视觉方向或暂停优先级。
- 需要总制作人确认后才能接受任何 v0.2 可观察行为差异、缩减验收路径、保留可运行旧卡牌兼容层或扩大到本阶段非目标。
- 禁止合并或推送 `master`、触发 Pages/公开部署、制作正式安装包，或代表 QA/项目所有者宣告最终验收。
